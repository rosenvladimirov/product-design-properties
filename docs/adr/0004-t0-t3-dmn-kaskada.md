# ADR-0004: T0–T3 DMN каскада като модел на изразяване на матрицата

- **Статус:** приет
- **Дата на решението:** ок. 2026-04…05 (в сила в кода)
- **Дата на записа:** 2026-07-13 (консолидация)
- **Взето от:** Росен Владимиров
- **Източник на реконструкцията:** memory `anchor_design_matrix_engine_digest_2026_07_05`, `project_base_zen_decision_2026_05_26` (изоморфизъм таблица); код `mrp_design_matrix/models`

## Контекст

Конфигураторът трябва да превърне параметрите на един лот (ширина, модел, клас…) в конкретен BoM: кои материали, с какви количества, кои операции. Това изисква подреден, детерминиран поток от решения, редактируем като данни.

## Разгледани алтернативи

1. **Едно голямо правило/таблица.** — Отхвърлено: несмилаемо, не разделя отговорностите.
2. **Императивен Python per продукт.** — Отхвърлено: клиентска логика в код (виж [ADR-0005](0005-klientska-specifika-kato-danni.md)).
3. **Каскада от четири ZEN таблици с ясни роли (T0–T3).** — Прието.

## Решение

Матрицата се изразява като каскада от 4 ZEN таблици (JSON на `mrp.bom`, копирани от `mrp.matrix.template`):
- **T0 `constraint_table`** — guard: ако е празна, матрицата НЕ тръгва (`action_confirm` gate).
- **T1 `geometry_table`** — извеждане на контекст (derive).
- **T2 `material_table`** — активиране/коефициенти на материалите (оценява се веднъж per MO).
- **T3 `operation_table`** — операции.

Моделът е **изоморфен** на `access_control` (A0–A3: credential guard → direction/window derive → accept/deny → effects) — същата ZEN семантика, друг домейн.

## Обосновка

Каскадата дава четими, разделени по отговорност слоеве, всеки редактируем като данни. T0-като-gate прави поведението предвидимо (без пълна T0 матрицата не се самоизпълнява). Изоморфизмът с access_control доказа, че T0–T3 не е ad-hoc, а общ модел — което мотивира извеждането на `base_zen_decision` ([ADR-0002](0002-izvezhdane-base-zen-decision.md)).

## Последици

- Move-генерацията при MO: `action_confirm` = стандартна експлозия + `_generate_design_matrix_moves` (само при наличен `constraint_table`); `qty_final = qty_base × coeff`.
- JDM форматът изисква строга дисциплина (виж [ADR-0003](0003-izbor-gorules-zen.md) последици).
- Двойно-move поведение при коефициенти беше по-късно коригирано ([ADR-0008](0008-base-zen-decision-mrp-glue.md) свързан фикс, git `676095c`).

## Произход на приноса (задължително, честно)

- Решението е взето от: **Росен** (моделът на изразяване е негов архитектурен избор).
- Имплементацията е: **с AI асистенция под надзор**.
- Забележки: точната дата на въвеждане на T0–T3 не е фиксирана с единичен комит — моделът е в кода отпреди извеждането на kernel-а; датата е приблизителна („ок. 2026-04…05").
