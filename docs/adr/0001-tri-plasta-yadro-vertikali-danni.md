# ADR-0001: Трипластова архитектура — ядро / отраслови вертикали / клиентски данни

- **Статус:** приет
- **Дата на решението:** 2026-05 (оформено; действащо в кода и по-рано)
- **Дата на записа:** 2026-07-13 (консолидация)
- **Взето от:** Росен Владимиров
- **Източник на реконструкцията:** memory `products/design_matrix/anchor_design_matrix_engine_digest_2026_07_05`, `topics/licensing/licensing_master_reference` §4; git история `product-design-properties`

## Контекст

Matrix конфигураторът се използва от няколко несвързани клиента и индустрии (Solid55 — дограма/врати; Teolino — ролетни щори; MEC — печатни платки/PCB; опаковки, храни). Всеки има различни продуктови правила. Възникна въпросът как един и същ софтуер да обслужва различни клиенти, без клиентската специфика да размива границата на собственост и да заразява ядрото.

## Разгледани алтернативи

1. **Един монолитен модул** с клиентска логика вътре (условия per клиент в общия код). — Отхвърлено: всяка клиентска промяна докосва общия код; blast radius върху всички клиенти; размива собствеността.
2. **Отделен форк per клиент.** — Отхвърлено принципно (виж [[feedback_no_private_forks_client_repos]]); дублира ядрото, поддръжката се разпада.
3. **Три пласта: споделено ядро + отраслови вертикали + клиентска конфигурация като данни.** — Прието.

## Решение

Системата се дели на три пласта:
1. **Ядро/двигател** — индустрия-агностично, винаги на Росен: `mrp_design_matrix`, `base_zen_decision`, `mrp_bom_line_formula_template`/wizard, конфигуратор.
2. **Отраслови вертикали** — отделни модули, които само `depends` на ядрото и добавят своите данни/правила + собствен код (напр. `mrp_design_matrix_security_door`, `_roller_door`, `_corrugated`, `_teolino_shutters`, `mrp_design_matrix_pcb`).
3. **Клиентска конфигурация** — ДАННИ (параметрични дефиниции, ZEN таблици, шаблони), не код. Виж [ADR-0005](0005-klientska-specifika-kato-danni.md).

Съответства на T1/T2/T3 нивата за лицензиране/собственост (licensing_master_reference §4).

## Обосновка

Разделението определя едновременно **техническата** граница (reuse без модификация) и **правната** граница на собственост и copyleft (кое остава у Росен, кое може да е на клиента). Това е носещо решение — промяната му би преструктурирала и кода, и лицензния модел.

## Последици

- Стана лесно: нов клиент/индустрия = нов вертикален модул без пипане на ядрото.
- Стана трудно/дисциплинирано: изкушението да се „бръкне" в ядрото за един клиент е забранено ([ADR-0005](0005-klientska-specifika-kato-danni.md)); при нужда — extension point във вертикала.
- Лицензната архитектура (T1/T2/T3) стъпва пряко върху този пласт-модел.

## Произход на приноса (задължително, честно)

- Решението е взето от: **Росен** (архитектурен избор; отразен и в лицензната рамка, обсъждана с адв. Костов).
- Имплементацията е: **с AI асистенция под надзора на Росен** (ядрото и вертикалите са разработвани в сесии с Claude; структурните решения са на Росен).
- Забележки: точната начална дата на трипластовия модел не е еднозначно фиксирана в git с един комит — моделът е еволюирал; датата „2026-05" е по memory и по времето на извеждането на `base_zen_decision` ([ADR-0002](0002-izvezhdane-base-zen-decision.md)).
